# Аудит существующих казахских полей (kk / labelKk)

Инвентаризация точек, где казахский язык **уже присутствует в коде и базе**, до
реализации системы локализации. Локализация не реализована, ни одно поле не удалено.

Дата: 2026-09-20. Связанные документы: `public-strings.csv`, `public-strings-summary.md`.

## Главный вывод

Модель данных для двух языков **уже существует сквозным образом** — от колонок Prisma
через репозиторий и доменный тип `LocalizedText` до `PublicCatalog`, который отдаёт
казахские значения в браузер. Не реализован только **уровень чтения**: каждый вызов в
интерфейсе жёстко берёт `.ru` / `labelRu`.

```
Prisma (*Kk колонки) → db-repository.ts → LocalizedText {ru, kk} → toPublicCatalog()
   → браузер получает kk → ❌ компонент читает только .ru
```

Ни один продакшен-путь не читает `.kk` или `labelKk`: поиск по `src/` вне слоя данных
не даёт ни одного обращения. То есть все казахские значения сегодня **доставляются, но
не используются**.

**Сохранить.** Это готовый источник казахских данных каталога.

### A3. Значения в сидах (114 вхождений `kk:`)

`src/lib/data/seed-data.ts` содержит казахские значения для: моделей, готовых

(`` `Тірек ${h.value} мм` ``, `` `Сөре ${meta.kk} ${width}×${depth}` ``).

колонке `notes` CSV как готовые варианты. **Сохранить и переиспользовать** — большинство
строк каталога переводить заново не потребуется.

Из 85 инлайновых пар `ru/kk` только 2 совпадают дословно (`MS Стандарт`, `Гараж`) — и
это корректно: бренд и заимствование, а не пропущенный перевод.

## B. Устаревшие / дублирующие

Полей с неверными или дублирующими значениями **не обнаружено**. Обнаружены две
несогласованности, которые стоит учесть при проектировании локализации:

### B1. `Locale` допускает `'en'`, которого нет в данных

`Locale = 'ru' | 'kk' | 'en'`, но `LocalizedText` имеет только `ru` и `kk`, и ни одной
английской строки в каталоге нет. Тип обещает третий язык, которого не существует.
Решить при проектировании: либо убрать `'en'`, либо сделать `LocalizedText` частично
необязательным. **Не трогал** — изменение типа вне задачи.

### B2. SEO-поля не локализованы, хотя выглядят локализованными

`ProductModel.seo` и `CatalogProduct.seo` — это `{ title: string; description: string }`
(колонки `seoTitle` / `seoDescription`), а **не** `LocalizedText`. При этом в схеме есть
отдельная неиспользуемая модель `SeoMetadata` с `titleKk` / `descriptionKk`. То есть
казахский путь для SEO как бы заявлен, но проходит мимо реальных SEO-данных.
Это структурный пробел для будущей локализации метаданных (строки SE-012…SE-021 в CSV).

## C. Сейчас не используются

### C1. Все без исключения казахские значения (уровень чтения)

Ни `.kk`, ни `labelKk` не читаются ни одним компонентом или страницей. Полный перечень
мест, где сейчас жёстко зашито `.ru` / `labelRu` и куда подключится будущая локаль:

| `src/components/layout/Header.tsx:35,89` | `link.labelRu` (десктопное и мобильное меню) |
| `src/components/layout/Footer.tsx:22` | `link.labelRu` |
| `src/app/page.tsx` | `model.name.ru`, `model.description.ru`, `useCase.ru` |

| `src/components/catalog/FilterForm.tsx` | `m.name.ru`, `u.ru` |
| `src/components/configurator/InstallDeliveryPanel.tsx` | `service.name.ru`, `method.name.ru`, `description.ru` |

| `src/app/api/orders/route.ts` | `model?.name.ru` (сохраняется в заказ) |

**Ничего не удалено**: эти значения — не мёртвый код, а данные, ожидающие уровня чтения.

### C2. `FOOTER_LINKS` не имеет `labelKk`

`src/lib/config/site.ts:90–98` — 7 ссылок футера только с `labelRu`, в отличие от
`NAV_LINKS`. Это **пробел**, а не устаревшее поле: казахские варианты уже предложены в
CSV (F-004…F-008). **Не добавлял** — это уже реализация локализации.

### C3. Модель `SeoMetadata` не используется ни одной строкой кода

`prisma/schema.prisma:666–674`. Ни `seoMetadata`, ни `SeoMetadata` не встречаются в
`src/`, `scripts/` или `prisma/seed.ts`. Единственное по-настоящему мёртвое место из
найденных, включая её `titleKk` / `descriptionKk`.

**Не удалял**: это миграция базы данных, а задача явно запрещает изменения БД, и
удаление не требуется для текущей работы. Вынесено на решение — либо задействовать при
локализации метаданных, либо удалить отдельной миграцией.

## Рекомендации к будущей системе локализации

1. Точка подключения уже есть: добавить чтение `LocalizedText` по активной локали
   (одна функция `t(text, locale)`), а не вводить параллельный словарь для каталога.
2. Данные каталога переводить заново не нужно — проверить и дополнить существующие `kk`.
3. Отдельный словарь понадобится только для статических строк интерфейса (кнопки,
   подписи, сообщения) — это и есть содержимое `public-strings.csv`.
4. Закрыть три пробела: `labelKk` у `FOOTER_LINKS`, локализация SEO-полей, определённость
   по `'en'` в типе `Locale`.
